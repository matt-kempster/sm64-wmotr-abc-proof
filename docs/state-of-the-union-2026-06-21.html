No-A ⇒ No-Fly: State of the Union

Where the proof stands on 2026-06-21 — what the theorem actually says, how it's built, every assumption it still rests on (with a difficulty grade for each), and some editorializing. Written deliberately without proof-assistant jargon: SM64 words and plain proof words only. (Prior edition: 2026-06-10.)

TL;DR. The theorem — "if the A button is never down on any frame, and no warp ever spawns Mario directly into a flying state, then Mario is never in a flying action" — is fully stated over the real decompiled game code and proved end-to-end, resting on 56 named assumptions. The headline change since June 10 is not the count (54 → 56) but the kind: the entire 202-body handler grind that was the bulk of the work is essentially gone — six of the seven action-handler families (stationary, moving, airborne, submerged, automatic, object) are now machine-walked end-to-end, the interaction system is closed, and roughly two dozen named single-function keystones (the ground/air/water step engines, the pole/hang/tornado/cannon helpers) have been discharged. What remains is qualitatively different and far smaller: one open handler census (12 cutscene bodies, pure grind), ~26 trust-frontier claims about never-decompiled functions (audio, collision raycasts, vector math — now the largest single category), the memory-layout and linking bookkeeping (25 facts, near-zero risk), and just 3 plumbing rows — down from 8, and already sharpened from the old over-broad "for all externals" shape. The theorem is not finished — but the research-shaped risk is gone; what's left is a short, named checklist.

1 · What the theorem says, in SM64 terms

Imagine a frame-by-frame run of the game: a starting memory state, then one frame after another, each frame reading the controller and updating Mario. The theorem (noA_no_spawn_never_flying_real_mwf) says:

  • IF the starting state is sane (Mario exists, his action isn't already flying-or-cannon, the global pointers point where they should — a checkable list of conditions, the kind a save state either satisfies or doesn't),
  • and at every frame boundary, the A bit of the controller data in memory is 0,
  • and no frame is a warp that spawns Mario directly into a flying action (the "start a level shot out of a cannon in the sky" case — excluded by assumption, not analyzed yet),
  • THEN at every reachable state, the 32-bit value sitting in Mario's action field is not a flying action.

The theorem exists in four nested versions, each one replacing an abstraction with the real thing — this is how the proof keeps itself honest, and the differences are the whole point of taking it seriously:

VersionWhat got real
…_lpThe per-frame step is the real linked program's execute_mario_action, but the controller input is still an abstract bit.
…_realThe input is the actual A bit read out of the controller struct in memory.
…_real_v2The set of functions a frame can reach is a computed census, not an abstract "everything reachable."
…_real_mwfThe "sane memory" precondition is a concrete, row-by-row invariant about the actual memory image — the sharpest statement, and the one this document audits.

Two things make this worth taking seriously rather than being a cartoon of the claim:

First, "the game" means the actual decompiled code. Every fact about SM64 in this proof comes from C source (the decomp) run through a mechanical compiler-frontend pipeline into the proof assistant. Nobody hand-wrote a model of act_walking; the proof reads the same AST the compiler would compile. The C files in scope: mario.c, all seven mario_actions_*.c files, interaction.c, mario_step.c, behavior_actions (the wind), level_update.c (warps). If the proof claims act_jump doesn't write the action field except through set_mario_action, that's because a machine read act_jump's real body, line by line, and checked.

Second, "a frame" means actually running the code. Each step of the run is a real big-step execution of execute_mario_action — the function that dispatches to the stationary/moving/airborne/submerged/cutscene/automatic/object handler groups — over the linked program, with all its real callees. The flying logic is inside the analyzed code, not assumed away.

The honest scope caveats (read these — unchanged from June 10)

  • The frame is Mario's action step. The per-frame step is one call of execute_mario_action (which includes interactions, quicksand, special floors, warps, the wind). It is not yet the entire game-loop frame — the level script, the camera, and other objects' behavior code running outside Mario's update aren't in the step relation. If some Goomba's behavior code wrote Mario's action field directly, the current theorem wouldn't see it. (Objects mostly interact with Mario through the interaction system, which is in scope — but "mostly" is a claim about the game, not yet a theorem.)
  • The spawn exclusion is an abstract bit. "No frame spawns Mario into flight" is a per-frame boolean the theorem takes as input. It models the warp/level-script path (set_mario_initial_action) which hasn't been analyzed. Eventually this should become a real claim about the warp code.
  • This is GOAL 1. GOAL 2 — "you cannot complete Wing Mario over the Rainbow without flying" (the actual route argument: red coins, the y-coordinate bound) — has not been started. GOAL 1 is the engine-level lemma it will sit on.

2 · The shape of the proof

The mathematical heart is one idea and one engineering decision.

The idea: track "tainted", not "flying". The obvious invariant — "Mario's action is never flying" — is not inductive, because of the cannon: you enter ACT_SHOT_FROM_CANNON on an A-press frame, but the handler writes ACT_FLYING on a later, A-free frame (if you have the wing cap). So a per-frame "no flying without A this frame" claim is simply false. The proof instead carries: Mario's action is never in the taint set T = {the flying actions} ∪ {ACT_FLYING_TRIPLE_JUMP, ACT_SHOT_FROM_CANNON}. Every door into T was found by machine census of every set_mario_action call site, and each door was proved to be A-gated: the dispatch into flying, the cannon fire (gated on the A bit read from memory — which the carried invariant says is clear), the three flying-triple-jump callers, one indirect site. Since T contains the flying set, "never tainted" gives "never flying" for free. The price is honest: the starting state must not already be mid-cannon-shot.

The decision: walk everything. "Does this function ever write Mario's action field?" sounds like a job for a clever pointer-analysis abstraction. Clever pointer abstractions over real C are where verification projects go to die. Instead the project built reusable walkers — proof machinery that takes a real function body and mechanically grinds through it statement by statement, discharging each store against a small set of proved "bricks": stores to Mario's non-action fields are fine (field-offset geometry), stores to known globals are fine (those globals live in different memory), stores through chased object pointers are fine (the pointer-chase invariant keeps them in the object pool, which is disjoint from Mario), stores to a function's own locals are fine, A-gated branches are dead code, and writes to the action field must go through the blessed setter family. Since June 10 the walkers have chewed through the entire handler backlog — well over a hundred more real bodies, including the four big "rest" families (stationary, moving, airborne, submerged) and a string of nasty multi-level helper subtrees (the ground/air/water quarter-step engines, hanging physics, the tornado, the cannon).

Memory safety is its own invariant. Underneath everything sits a concrete ten-or-so-row invariant about the memory image, proved preserved by every step: the A bit is clear in both the controller struct and Mario's mirrored input halfword; the action field always holds a real 32-bit value; gMarioState points at Mario; Mario's object pointers (marioObj, heldObj, usedObj, interactObj…) point into the object pool; anything you reach by chasing pointers from the pool stays in the pool; the interaction-handler table only ever yields the 29 known handler functions. This is what kills the "but C has pointers, anything could write anywhere" objection — not by hand-waving, but as a maintained, machine-checked invariant.

Judgment. All true for boring reasons (separate C objects don't overlap; globals are allocated at startup and never freed). Self-contained, fully standard, no SM64 cleverness required; sequence it late, in one pass.

3.6 · The trust frontier — ~26 claims about never-decompiled functions trust frontier

The proof therefore assumes a specific, small behavior contract for each. This is now the largest single category in the ledger — not because it grew, but because everything around it shrank. Honesty note: the compiler model's baseline assumption about unknown external functions is that they may write any memory, so these rows are genuine additional trust — and they are exactly the list of what is being trusted. Each is the kind of claim a person can check against the decomp in minutes.

Judgment. A decision is owed here, and I'd make it explicitly rather than drift: either (a) declare this the documented model boundary — the final theorem reads "…assuming these ~26 named functions behave as stated", defensible because each claim is tiny and auditable; or (b) shrink it by decompiling more files. If shrinking, the two high-value targets are obvious: surface_collision.c retires the whole collision cluster and math_util.c retires the vector/math cluster — together more than half the frontier, both small, self-contained, loop-heavy-but-pointer-simple C the existing walkers should handle. Audio and camera I'd leave on the frontier forever; nobody doubts play_sound doesn't grant flight, and the audio system is a huge dependency swamp.

3.7 · The plumbing — 3 rows left, already sharpened real work

June 10 flagged 8 over-broad "for all externals / any function" rows as the risk concentration. Five are now gone (discharged or merged into §3.6), and the three that remain have already been restated from the dangerous "for all" shape into the safe "only the functions a frame actually reaches" shape — the exact refactor the project's own post-mortems prescribe. The over-broad versions (including the deleted Hret_ext) were provably false for the real program — they admitted memcpy/vload adversaries the game never invokes — and have been deleted.

5 · What I actually think

The character of the proof has flipped. A month ago the honest summary was "a 202-body checklist plus some risky old plumbing." Today the checklist is 12 cutscene bodies, the risky plumbing is three sharpened rows, and the dominant remaining item is a decision, not a problem: how much of the game's math/collision/audio C to keep trusting versus decompile. That is a much healthier place to be — the remaining work is almost entirely either mechanical burn-down or a deliberate scoping call, with very little "and here we hope an idea shows up."

The load-bearing insight is still the taint set, and the brute-force bet has paid in full. The cannon is the whole ballgame: any sketch that says "flying requires A on the same frame" is false, and building the invariant around "shot-from-cannon counts as already-flying" is what makes this engage the real game rather than a story about it. And the walk-everything bet — build a new proof arm whenever the C does something new, then reuse it — has now consumed the entire handler set including the genuinely hard helpers (the step engines, hanging, the tornado, the cannon's A-gated dead branch). The toolkit is mature; new bodies are cheap unless they're truly novel, and novelty is now rare.

Where I'd spend skepticism, in order. (1) The trust frontier — it's fine if declared, corrosive if it silently grows; I'd institute a hard rule that the frontier only shrinks, and I'd retire surface_collision.c and math_util.c to cut it roughly in half. (2) The frame-scope caveat — "Mario's action step" is still not "the whole game frame," and closing that gap (level script, other objects' direct writes) is a real future arc, not a footnote. (3) The startup-memory story for §3.4/§3.5 — standard, but unwritten, and everything leans on it; I wouldn't want it to be the thing discovered to be subtly wrong at the end.

What's left is small, but GOAL 2 is the iceberg. Finishing GOAL 1 from here — 12 cutscene bodies, the startup story, the linking pass, and a decision on the frontier — is weeks, not months, and almost none of it is research. But GOAL 2 (the actual Wing-Mario-over- the-Rainbow route argument: red coins, the y-coordinate bound, the level geometry) has not been started, and it is a different kind of proof entirely. GOAL 1 is the engine lemma it stands on; it is nearly a checklist now, but it is the foundation, not the building.

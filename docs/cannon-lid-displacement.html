Cannon Lid Displacement

On its last frame the WMotR cannon lid deletes itself but still loads its floor, so Mario's platform pointer can be left naming a freed object slot. If a spinning object is spawned into that slot before the next frame's platform step, Mario is rotated around it and thrown up to thousands of units in one frame.

Found 2026-11-07 while proving the A-button-challenge height bound for WMotR. Demonstrated in the real game with memory hacks. Not reachable in normal play, as far as we can tell.

Background: platform displacement

The game keeps one pointer, gMarioPlatform, to the object Mario is standing on. Each frame, apply_mario_platform_displacement moves Mario by that object's velocity and, if it spins, rotates him around the object's centre by its angular velocity. At the end of each frame, update_mario_platform looks up Mario's floor and sets the pointer again.

The pointer is only a slot address in the 240-slot object pool. When an object is deleted its slot goes on a last-in-first-out free list, and the next spawned object takes it. A pointer that is not cleared in time starts naming whatever object is spawned there next.

A known relative is spawning displacement on the Japanese version: there the pointer is not cleared on area transitions (spawn_objects_from_info calls clear_mario_platform only #ifndef VERSION_JP). Cannon lid displacement is an intra-level version that also exists on the US version.

What is special about the lid

Most solid objects drop their collision before they are deleted. The exclamation box spends 7 frames with no surfaces before it is removed, and the blue coin switch hides and stops loading collision long before it deletes itself. The cannon lid does it in the other order. At opening timer 80, cannon_door_act_opening calls bhv_cannon_closed_init, which marks the lid deleted and returns. The lid's behavior script then continues to its next command, which loads its collision model:

// cannon_door.inc.c
if (o->oTimer == 80) {
    bhv_cannon_closed_init();      // spawns the cannon, activeFlags = DEACTIVATED
    return;
}
// bhvCannonClosed then runs CALL_NATIVE(load_object_collision_model)

So for one frame the lid is already deleted but its floor is still in the collision data. In WMotR only two object types load collision at all, the exclamation box and this lid, so the lid is the only object in the level with this property.

The sequence

Each frame, update_objects runs the steps below in this order. The pointer is set at the end of frame N and read early in frame N+1.

Frame N lid's last frame

  1. update_terrain_objects: the lid reaches timer 80, deletes itself, then still loads its floor.
  2. Mario updates. He must be standing on the part of the lid still over the cannon hole, an 8-unit-wide sliver.
  3. unload_deactivated_objects: the lid's slot goes to the front of the free list.
  4. update_mario_platform: Mario's floor is the lid's floor, so gMarioPlatform now names the freed slot.

Frame N+1 the fling

  1. clear_dynamic_surfaces: the lid's floor is gone; the pointer is not updated yet.
  2. update_terrain_objects: an exclamation box breaks this frame and spawns its contents, mist, then 20 debris triangles, each with pitch spin 0x80 * (rand + 50), about 35°. One triangle must land in the lid's old slot.
  3. apply_mario_platform_displacement: Mario is rotated 35° around that triangle.
  4. update_mario_platform: the pointer is corrected. The effect lasts one frame.

Demonstration

Run in the real US game (the matching decomp build in Mupen64Plus), starting from a WMotR save state. All game code runs unmodified; the hacks are memory writes.

  • Hack 1: set the cannon-unlocked save bit directly, so the lid opens without the Bob-omb Buddy's cutscene, which normally freezes Mario.
  • Hack 2: place Mario on the lid, and on its last frames on the exposed sliver 108 units behind its centre.
  • Hack 3: once gMarioPlatform names the freed slot, fill that slot the way a debris triangle would: zero it as allocate_object does, place it at a box position plus 100 in y, and give it pitch spin 6400.

The stale pointer itself needed no hack: with Mario on the sliver, the game set gMarioPlatform to the freed lid slot on its own.

Why it does not happen in normal play

The lid only opens after you talk to the Bob-omb Buddy. Mario stays in the talking action through the whole cannon-opening cutscene, and the lid finishes opening (60 + 80 frames after the unlock) inside that cutscene, about 540 units away from Mario. If the cannon is already open when you enter the level, the lid deletes itself on its first frame while Mario is at the start.

Even without the freeze, all of these would have to line up:

  • Mario stands on an 8-unit sliver of the lid on its last frame. Further forward he is on the ground; further back he is over the hole.
  • An exclamation box breaks on exactly the next frame, so Mario must have hit it about 8 frames earlier. The nearest box is 260 units away and 260 units up.
  • A debris triangle, not the box's contents, gets the lid's slot. The freed slot is at the front of the free list, so the contents take it unless other objects were deleted after the lid in the same frame.

Where it matters

It came up in a machine-checked proof that, without pressing A, Mario cannot gain height in WMotR beyond a fixed bound. Part of that proof is a rule that the object Mario stands on never spins, which rules out platform-displacement height gains. This sequence is the one way that rule could break in WMotR, so the proof relies on a labeled assumption about the cannon cutscene's length (Hcam_cannon_cutscene) until the camera code is brought into the proof.

A rough scan of the whole game found 17 solid object behaviors that can delete themselves, but the ones checked so far drop their collision first. Whether any other object repeats the lid's order of events is open.

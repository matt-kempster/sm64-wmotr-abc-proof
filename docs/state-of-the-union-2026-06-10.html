No-A ⇒ No-Fly: State of the Union

Where the proof stands on 2026-06-10 — what the theorem actually says, how it's built, every assumption it still rests on (with a difficulty grade for each), and some editorializing. Written deliberately without proof-assistant jargon: SM64 words and plain proof words only.

TL;DR. The theorem — "if the A button is never down on any frame, and no warp ever spawns Mario directly into a flying state, then Mario is never in a flying action" — is fully stated over the real decompiled game code and proved end-to-end, resting on 54 named assumptions. Zero of those assumptions are "and then a miracle occurs": each one is a finite, specific claim about specific functions or specific memory. The bulk (by labor) is 202 action-handler function bodies still waiting to be machine-walked — pure grind with machinery that already exists and has chewed through the hardest cases (poles, hanging, tornado, the cannon). The riskiest items are 8 old "plumbing" assumptions that are stated more broadly than they should be and need restating before they can be discharged. The most philosophical item is the trust frontier: ~30 claims about functions whose C source was never fed into the pipeline (audio, collision raycasts, vector math). The theorem is not finished — but at this point it is a checklist, not a research problem.

1 · What the theorem says, in SM64 terms

Imagine a frame-by-frame run of the game: a starting memory state, then one frame after another, each frame reading the controller and updating Mario. The theorem (noA_no_spawn_never_flying_real_mwf) says:

  • IF the starting state is sane (Mario exists, his action isn't already flying-or-cannon, the global pointers point where they should — a checkable list of conditions, the kind a save state either satisfies or doesn't),
  • and at every frame boundary, the A bit of the controller data in memory is 0,
  • and no frame is a warp that spawns Mario directly into a flying action (the "start a level shot out of a cannon in the sky" case — excluded by assumption, not analyzed yet),
  • THEN at every reachable state, the 32-bit value sitting in Mario's action field is not a flying action.

Two things make this worth taking seriously rather than being a cartoon of the claim:

First, "the game" means the actual decompiled code. Every fact about SM64 in this proof comes from C source (the decomp) run through a mechanical compiler-frontend pipeline into the proof assistant. Nobody hand-wrote a model of act_walking; the proof reads the same AST the compiler would compile. The C files in scope: mario.c, all seven mario_actions_*.c files, interaction.c, mario_step.c, behavior_actions (the wind), level_update.c (warps). If the proof claims act_jump doesn't write the action field except through set_mario_action, that's because a machine read act_jump's real body, line by line, and checked.

Second, "a frame" means actually running the code. Each step of the run is a real big-step execution of execute_mario_action — the function that dispatches to the stationary/moving/airborne/submerged/cutscene/automatic/object handler groups — over the linked program, with all its real callees. The flying logic is inside the analyzed code, not assumed away.

The honest scope caveats (read these)

  • The frame is Mario's action step. The per-frame step in the theorem is one call of execute_mario_action (which includes interactions, quicksand, special floors, warps, the wind). It is not yet the entire game-loop frame — the level script, the camera, and other objects' behavior code running outside Mario's update aren't in the step relation. If some Goomba's behavior code wrote Mario's action field directly, the current theorem wouldn't see it. (Objects mostly interact with Mario through the interaction system, which is in scope — but "mostly" is a claim about the game, not yet a theorem.)
  • The spawn exclusion is an abstract bit. "No frame spawns Mario into flight" is a per-frame boolean the theorem takes as input. It models the warp/level-script path (set_mario_initial_action) which hasn't been analyzed. Eventually this should become a real claim about the warp code.
  • This is GOAL 1. GOAL 2 — "you cannot complete Wing Mario over the Rainbow without flying" (the actual route argument: red coins, the y-coordinate bound) — has not been started. GOAL 1 is the engine-level lemma it will sit on.

2 · The shape of the proof

The mathematical heart is one idea and one engineering decision.

The idea: track "tainted", not "flying". The obvious invariant — "Mario's action is never flying" — is not inductive, because of the cannon: you enter ACT_SHOT_FROM_CANNON on an A-press frame, but the handler writes ACT_FLYING on a later, A-free frame (if you have the wing cap). So a per-frame "no flying without A this frame" claim is simply false. The proof instead carries: Mario's action is never in the taint set T = {the flying actions} ∪ {ACT_FLYING_TRIPLE_JUMP, ACT_SHOT_FROM_CANNON}. Every door into T was found by machine census of every set_mario_action call site, and each door was proved to be A-gated: the dispatch into flying, the cannon fire (gated on the A bit read from memory — which the carried invariant says is clear), the three flying-triple-jump callers, one indirect site. Since T contains the flying set, "never tainted" gives "never flying" for free. The price is honest: the starting state must not already be mid-cannon-shot.

The decision: walk everything. "Does this function ever write Mario's action field?" sounds like a job for a clever pointer-analysis abstraction. Clever pointer abstractions over real C are where verification projects go to die. Instead the project built reusable walkers — proof machinery that takes a real function body and mechanically grinds through it statement by statement, discharging each store against a small set of proved "bricks": stores to Mario's non-action fields are fine (field-offset geometry), stores to known globals are fine (those globals live in different memory), stores through chased object pointers are fine (the pointer-chase invariant keeps them in the object pool, which is disjoint from Mario), stores to a function's own locals are fine, A-gated branches are dead code, and writes to the action field must go through the blessed setter family. Each new function is then cheap — unless it uses a pattern no walker arm handles yet, in which case a new arm gets built once and reused forever. Roughly seventy real function bodies have been walked end-to-end this way so far, including some genuinely nasty ones (a 730-line pole-positioning helper, hanging physics with collision out-parameters, the tornado's local arrays, the cannon).

Memory safety is its own invariant. Underneath everything sits a concrete ten-or-so-row invariant about the memory image, proved preserved by every step: the A bit is clear in both the controller struct and Mario's mirrored input halfword; the action field always holds a real 32-bit value; gMarioState points at Mario; Mario's object pointers (marioObj, heldObj, usedObj, interactObj…) point into the object pool; anything you reach by chasing pointers from the pool stays in the pool; the interaction-handler table only ever yields the 29 known handler functions. This is what kills the "but C has pointers, anything could write anywhere" objection — not by hand-waving, but as a maintained, machine-checked invariant.

3.6 · The trust frontier — ~30 claims about never-decompiled functions trust frontier

These functions are called by analyzed code but their own C was never fed through the pipeline (they live in math_util.c, surface_collision.c, the audio and camera systems…). The proof therefore assumes a specific, small behavior contract for each. Important honesty note: the compiler model's baseline assumption about unknown external functions is that they may write any memory — so these rows are genuine additional trust, and they are exactly the list of what is being trusted. Each one is the kind of claim a person can check against the decomp in minutes.

A decision is owed here, and I'd make it explicitly rather than drift: either (a) declare this the documented model boundary — the final theorem reads "…assuming these ~30 named functions behave as stated", which is defensible because each claim is tiny and auditable; or (b) shrink it by decompiling more files. If shrinking, the two high-value targets are obvious: surface_collision.c retires the whole collision cluster (6 rows) and math_util.c retires the vector/math cluster (~8 rows) — together more than half the frontier, and both files are small, self-contained, loop-heavy-but-pointer-simple C that the existing walkers should handle. Audio and camera I would leave on the frontier forever; nobody doubts play_sound doesn't grant flight, and the audio system is a huge dependency swamp.

3.7 · The plumbing — 8 rows, the oldest layer needs restating

These survive from the earliest engine and are stated with a breadth the project has since learned to ban ("for all externals…", "for any function…" — when the program only ever calls a specific finite set). As written, several can't be proved — not because they're morally wrong, but because they quantify over adversarial cases the real program never produces. They need to be split into per-function claims (which then mostly merge into §3.6) — restatement work, not discovery work.

AssumptionWhat it saysJudgment
Hext, Hmwf_ext, Hext_actionAny external call preserves the A-clear fact, the taint fact, and the memory invariant.Over-broad on purpose (placeholder). Should become: an enumeration of the actual externals reachable in a frame, each row then living in §3.6. Mostly mechanical once someone sits down to do it; touches the engine's core lemma, so it will ripple — do it deliberately.
Hret_extNo external call returns a pointer to Mario's struct.Same restatement; per-function it's easy (most return ints/floats; spawn_object returns a pool slot).
Hret_callNo analyzed function that returns a pointer returns Mario's struct.The reached set is concrete, so this is per-body return-value analysis — grind-shaped, and the walkers already track return values for some bodies. Medium.
HrestAny call handed Mario's pointer preserves A-clear plus two structural facts about gMarioState/marioObj.The "for any function" twin of the per-symbol surface that already exists (§3.1's censuses are its sharpened replacement for the dispatch tree). Needs the same enumeration treatment.
Hstore, HstoremwfAn assignment passing the (syntactic) provenance check preserves the facts.Quantified over all environments — the precise shape the project's own post-mortems call a phantom. The newer walkers prove the same thing execution-relative; these two rows should be re-derived from that machinery and deleted.

Judgment. This is the part I'd flag to a skeptical reviewer first, and the part I'd most want retired soon — not because the claims are implausible (per-function they're all boring) but because over-broad assumptions are exactly where false confidence hides. The good news: the project has done this same refactor four times already (the false "for-all" frame check, the for-all-functions reach split, the for-all-objects handler contracts, the find_floor row) and each time the sharpened version went through.

5 · What I actually think

The structure is sound, and the load-bearing insight is the taint set. The cannon is the whole ballgame: any proof sketch that says "flying requires A on the same frame" is just false, and the fact that this proof hit that wall, recognized it, and rebuilt the invariant around "shot-from-cannon counts as already-flying" is the strongest evidence the project is engaging with the real game rather than a story about it. The A-gate census — every door into the taint set, found by machine, each proved to require the A bit — is the part I'd show an SM64 person first.

The brute-force bet paid off. Walking ~70 real decompiled bodies, building a new proof "arm" every time the C does something new (out-parameters, local arrays, loops, function-pointer tables, A-gated dead code) is unglamorous, but every alternative — hand-modeling functions, clever whole-program pointer abstractions — either reintroduces the "did you model it right?" trust hole or collapses under real C. The walker toolkit is now mature enough that the cannon (which needed three different new mechanisms a month ago) went down in a day. That's what makes the 202 a checklist and not a threat.

Where I'd spend skepticism. In order: (1) the eight plumbing rows — over-broad statements are where a vacuous or unsatisfiable assumption could lurk, and the project's own history says every one of these eventually needed restating; (2) the frame-scope caveat — "Mario's action step" is not "the whole frame", and closing that gap (level script, other objects' direct writes) is a real future arc, not a footnote; (3) the trust frontier — fine if declared, corrosive if it silently grows. I'd institute a rule that the frontier only shrinks.

What's left is smaller than what's done, but it isn't small. The grind has been running at very roughly 5–15 bodies per session-day when no new machinery is needed. 202 + ~29 bodies, a few of which will surely demand new arms, plus the plumbing restatement, the startup story, and the linking pass — that's on the order of weeks of sustained work, not days, and GOAL 2 (the actual Wing-Mario-over-the-Rainbow route argument) is still entirely ahead. But the character of the remaining work has changed completely since a month ago: there is no longer any step where the plan is "and here we hope an idea shows up." Every open item has a name, a shape, and a known tool.

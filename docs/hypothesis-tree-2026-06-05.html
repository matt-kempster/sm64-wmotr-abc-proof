Every hypothesis under the proof

The complete, unelided inventory of what noA_no_spawn_never_flying_real_mwf — the sharpest live GOAL-1 capstone — rests on, as of 2026-06-05 (commit 91169ad), with each assumption explained in plain terms. If an assumption is not on this page, the proof does not make it.

How to read this page. The proof source contains zero Admitted / Axiom / sorry. Every remaining gap is an explicit, named Hypothesis or Variable of one Coq section, and Print Assumptions on the theorem returns exactly 9 standard axioms (re-verified today; reproduced verbatim in §3). So the full distance to an unconditional theorem is finite and enumerable, and this page enumerates all of it: 9 axioms (the trust floor) · 6 abstract objects (awaiting concrete witnesses) · 38 named hypotheses in 7 groups (§5–§11) · 4 per-run premises written into the statement itself (§12). Nothing is elided.

1 · The theorem, in one breath

The capstone (proofs/NoAImpliesNoFly/NoAImpliesNoFlyLinked.v, section NoARealInputMWF), verbatim:

Theorem noA_no_spawn_never_flying_real_mwf :
  forall (init : mem) (is : list mem) (m : mem),
    mem_ok_lp lp bm MWF init ->                          (* P1: a sane starting state *)
    Forall (fun i => a_pressed_real bm i = false) is ->  (* P2: A is never pressed *)
    Forall (fun i => spawn_flying i = false) is ->       (* P3: no spawn-into-flying *)
    reachable mem mem (step_real lp) init is m ->        (* P4: m reached by REAL frames *)
    ~ mem_flying_lp bm m.                                (* Mario is never flying *)

In plain terms: start the game in any sane state where Mario is not already flying (or mid-cannon-shot). Play any number of frames, where each frame is literally one execution of the compiled C function execute_mario_action — the mechanically translated (clightgen'd) decompiled SM64 source, not a hand-written model. If on every one of those frames the controller's A button is not pressed, and no level-script warp spawns Mario directly into a flying state, then at the end Mario's action variable does not hold ACT_FLYING or ACT_FLYING_TRIPLE_JUMP. You cannot fly without pressing A.

Three definitions make the statement honest rather than abstract:

  • a_pressed_real — "A was pressed" is read out of memory itself: follow Mario's controller pointer (offset 156 in his struct), read the buttonPressed halfword (offset 18 in the controller), test bit 0x8000 (the A button). Pessimistically: if the controller is unreadable, that counts as pressed, so the "no A" premise can only get stronger, never silently vacuous.
  • step_real — a frame's "input" is the pre-frame memory, and the step is one big-step execution (eval_funcall) of the real f_execute_mario_action over the linked program. There is no abstract input or transition model left in the statement.
  • mem_flying_lp — "Mario is flying" means: loading the 4-byte action field at offset 12 of his struct yields one of the two flying constants (0x10808899, 0x03000894), as read off the generated AST.

4 · The six abstract objects — placeholders awaiting witnesses

These are section Variables: not facts, but names for things the theorem is parametric in. Each will eventually be replaced by (or instantiated with) a concrete witness; until then, everything known about them flows through the 38 hypotheses.

lp : Clight.program
the linked game
The whole program obtained by linking all the compiled C files (mario.c, the seven mario_actions_*.c, interaction.c, behavior_actions.c, level_update.c, mario_step.c, …). It is kept abstract because computing the link inside Coq exhausts memory; instead, everything the proof needs to know about it is pinned per-file by the §5 link hypotheses — which is exactly what makes the assumption surface honest.
bm : block
Mario's struct
The memory block holding Mario's struct MarioState — his action (offset 12), input flags (offset 2), controller pointer (offset 156), object pointers (136/148/152), etc. It is a runtime block: the global gMarioState is an uninitialized pointer, so Mario's struct is wherever the engine put it, not a named global.
bc : block,  oc0 : ptrofs
the controller
Where the active controller struct lives: its memory block and its offset within that block. The A-button bit the whole theorem is about is the 0x8000 bit of the halfword at bc, oc0+18.
SafeB : block → Prop
the safe write-set
The set of memory blocks the frame is allowed to write into via chased object pointers — think: the object pool, Mario's body-state and camera-status structs. Its defining property (enforced by §6 and by MWF_real's rows R6/R7) is that nothing in it is Mario's struct or the controller, so writes through chased pointers can never touch the action field or the A bit. Its concrete instantiation (the object-pool story) is a known upcoming brick.
spawn_flying : mem → bool
the spawn oracle
A per-frame bit meaning "this frame, the level script / warp system spawns Mario directly into a flying state" (e.g. the start-of-level cutscene warp). That code path lives outside the per-frame action function, so the theorem excludes it by premise P3 rather than analyzing it. GOAL 2 territory.

5 · Group A — the 13 link-assembly pins open · link-time

None of these says anything about behavior. They say how the binary is put together: that the linked program lp really contains the code of each compiled C file, unchanged. In CompCert's vocabulary, linkorder p lp means "everything p defines appears in lp verbatim; linking may only fill in p's externals, never replace or alter its definitions." Each pin is a theorem of CompCert's linking metatheory (link_linkorder) the moment the link is exhibited — they are hypotheses only because the link itself is kept symbolic (§4, lp).

LO_mario : linkorder mario.prog lp
the root pin
The linked game contains mario.c's compiled code — in particular the real execute_mario_action the theorem steps, the real set_mario_action, and the real struct layouts (action at offset 12, etc.).
LO_sta · LO_mov · LO_air · LO_sub · LO_cut · LO_aut · LO_obj · LO_int · LO_beh · LO_lvl · LO_stp
11 per-file pins, same shape: linkorder mario_actions_stationary.prog lp, …
The linked game contains, verbatim, the compiled code of each of the seven action-handler files (mario_actions_{stationary, moving, airborne, submerged, cutscene, automatic, object}.c) plus interaction.c, behavior_actions.c, level_update.c and mario_step.c. Why they matter: they are what turns "some unknown function named mario_execute_airborne_action" into "THE generated body of that function, whose every statement we can enumerate" — the §8 residuals are statements about those pinned real bodies, not about adversarial stand-ins.
Hrest_ext_only
the negative pin — "no game logic hides behind a library name"
Hypothesis Hrest_ext_only : forall fid f,
    mem_id fid exempt_callees = true \/ fid = mario._play_infinite_stairs_music ->
    ~ resolves_lp lp fid (Internal f).
The 16 whitelisted helpers (sqrtf, atan2s, print_text_fmt_int, set_camera_mode, vec3f_set, stop_cap_music, fadeout_cap_music, f32_find_wall_collision, find_floor, vec3f_copy, vec3f_find_ceil, find_ceil, find_poison_gas_level, find_water_level, play_sound, vec3s_copy) and play_infinite_stairs_music have no C body in the linked program — they stay external. In plain terms: nobody can smuggle action-writing game logic into the proof's blind spot by naming it sqrtf. Satisfiable by construction: none of the linked source files defines any of these names.

6 · Group B — 5 layout facts + 1 whitelist lookup open · init-time / per-symbol

CompCert's memory model gives every C object (each global, each allocation) its own block; pointers cannot wander between blocks. These five hypotheses say the specific blocks of this run are pairwise distinct — "different C objects really are different objects." They are facts about the run's initial memory, dischargeable from initialization (distinct globals get distinct blocks; allocations are fresh).

Hbc_bm : bc <> bm
The controller struct is not inside Mario's struct. (A write to the controller can never be a write to Mario's action, and vice versa.)
HSafeB_not_bm : forall b, SafeB b -> b <> bm
Nothing in the safe write-set is Mario's struct — so object-field writes through chased pointers can never hit the action field.
HSafeB_not_bc : ~ SafeB bc
The controller is not in the safe write-set either — so those same writes can never set the A-button bit and fake a press.
Hgms_blk
the global pointer cell is its own object
The global variable gMarioState (the pointer cell that holds Mario's address) lives in its own block, distinct from Mario's struct, the controller, and the safe set.
Hglob_blk
written globals are their own objects
Every global on the censused "the frame writes this" list — currently exactly one, gCameraMovementFlags — lives in its own block, distinct from Mario's struct, the controller, and the safe set. (The frame may scribble on camera flags freely; it cannot thereby touch the action or the A bit.)
WL_exempt
the whitelist is really exempt — per-symbol lookup fact
When code calls one of the 16 whitelisted helper names, the function the linked program actually resolves it to is "exempt" from the Mario-pointer calling discipline: it is external, or its first parameter is not a MarioState*. In plain terms: find_floor and friends don't receive Mario as their first argument, so the engine doesn't owe them the Mario-argument bookkeeping. Dischargeable per symbol, like the pins.

7 · Interlude — MWF_real, the run invariant every residual references

"Memory is well-formed" (MWF), concretely — 8 rows, all about real offsets

Most remaining hypotheses say some piece of code "preserves MWF". MWF_real (proofs/MarioModel/MWFReal.v) is not an abstract promise — it is this checklist about the run's memory:

  1. R0 — the cast exists: Mario's block, the controller's block, the gMarioState global's block, and every safe-set block are live (allocated, not freed).
  2. R1 — mid-frame A flag clear: Mario's input halfword (offset 2) has the INPUT_A_PRESSED bit (0x0002) clear, whenever it reads as an integer.
  3. R2 — the controller pointer is honest: Mario's controller field (offset 156), if it holds a pointer, points exactly at the controller (bc, oc0).
  4. R3 — the button word is A-clear: the controller's buttonPressed halfword (offset 18), if it reads as an integer, has the A bit (0x8000) clear.
  5. R4 — the action is a number: the action field (offset 12) never holds a pointer — it is an integer or undefined, so it cannot be abused as a write target.
  6. R5 — gMarioState points at Mario: the global pointer cell, if it holds a pointer, holds exactly Mario's address (bm, 0).
  7. R6 — chase roots land in the safe set: Mario's three object-pointer fields (marioObj@136, statusForCamera@148, marioBodyState@152), if they hold pointers, point into SafeB.
  8. R7 — the safe set is closed: following any pointer stored inside a safe block lands in a safe block. (So arbitrarily long pointer chases starting from R6 never escape.)

All 14 obligations the v2 capstone places on its invariant (projections like "MWF implies the A bit is clear", and stability across function entry, stack frees, censused stores, and the input-update routine) are proved lemmas for MWF_real — that was the 06-04 milestone. What remains assumed about MWF is only: the §6 distinctness facts it leans on, that it holds at frame zero (premise P1), and that externals respect it (§10).

8 · Group C — the 11 per-body residuals open · the crux

This is the heart of the proof — the leaves where the actual game logic lives. All eleven share one shape, body_pres (proofs/MarioModel/RestSurface.v):

Definition body_pres (NoA MWF : mem → Prop) (bm : block) (f : Clight.function) : Prop :=
  forall m vargs t m' vres,
    (marg_exempt (Internal f) = false -> marg_ok bm vargs) ->   (* called with Mario's real pointer *)
    eval_funcall function_entry2 (lp_ge lp) m (Internal f) vargs t m' vres ->
    NoA m -> MWF m -> Mem.valid_block m bm ->
    action_sat not_tainted m bm ->                              (* action ∉ T before *)
    Mem.valid_block m' bm /\ action_sat not_tainted m' bm /\ MWF m'.  (* … and after *)

In plain terms, each residual says: take THE real compiled body of one specific function (pinned to the generated AST by §5 — there is no "for all functions" left). Call it the way the frame calls it, passing Mario's actual address. Start from a state where the A button is not pressed, memory is well-formed (§7), and Mario's action is outside the taint set T. Then when the call returns: Mario's action is still outside T, and memory is still well-formed.

Here T = {ACT_FLYING, ACT_FLYING_TRIPLE_JUMP, ACT_SHOT_FROM_CANNON} — flying plus the one non-flying action whose handler writes flying on a later, A-free frame (the cannon shot: wing cap + pure physics). Carrying "not in T" instead of "not flying" is what makes the invariant inductive; "no flying" follows because T contains the flying set.

Why each is believed true (the discharge story): in the decompiled source, every entry into a T action sits behind an A-press test (input & INPUT_A_PRESSED or the cannon's button gate) — and those gate-kill facts are already proved as semantic lemmas (AGates.v: the dispatch kill, cannon-fire kill, the three side-flip feeders, the landing-cancel indirect site, the button-update bridge). What remains is the per-body walk that threads them through each function's statement tree.

The decomposition lemma rest_pres_decompose (also proved) is what turned the old single adversarial assumption "every unknown rest function behaves" into exactly these eleven named statements about real code: an abstract linked program can no longer hide arbitrary code behind a rest symbol.

9 · Group D — return-value non-aliasing open

The engine tracks where Mario's address can flow. Two hypotheses close the one channel the census doesn't inspect: function return values.

Hret_call
no reached function returns Mario's address
If any function the frame reaches returns a pointer, that pointer is not into Mario's struct. Plain: you can't launder Mario's address through a return value and then write through it behind the analysis's back. Believed-true shape: the reached functions return void, numbers, or pointers to floors/ceilings/objects — never MarioState*. Discharge route: a return-expression census per reached body.
Hret_ext
no external returns Mario's address
Same statement for external (library) calls — find_floor returns a floor, spawn_object returns an object-pool slot, math returns numbers. Part of the external contract (§10).

10 · Group E — the external-call contract open · residual by design

Externals are functions with no C body anywhere in the linked sources (math builtins, sound, OS). CompCert axiomatizes them (§3), so "what they do to memory" is not provable even in principle — it must be assumed. The design keeps this unavoidable residual minimal and names it precisely:

Hext_action
externals never write the action
No external call modifies the 4 bytes of Mario's action field. (True of the real externals: sound code writes audio buffers, math writes nothing.)
Hmwf_ext
externals preserve well-formedness
No external call breaks any row of the §7 checklist — they don't redirect Mario's controller pointer, don't set the A bit, don't free Mario's block.
Hext
the bundled form consumed by the frame wrapper
The same promise in the older wrapper's vocabulary: an external call preserves the A-clear fact, the wrapper's memory-invariant bundle (action ∉ T, the two pointer-chase facts), and MWF, all at once. Overlaps §10's other two plus §11; kept because the v1 frame wrapper the v2 engine rides on still consumes this exact shape.

11 · Group F — wrapper duties open · slated for subsumption

Three obligations stated in the vocabulary of the first-generation frame wrapper (RealFrameLinked.v), which the newer engine still rides on. Their content overlaps groups C–E; they survive as separately-named hypotheses until the per-body machinery is extended to subsume them.

Hrest : reach_rest_marg_lp lp bm (NoA_real bm)
reached calls preserve the chase facts
Any function call the frame makes, given Mario's real pointer, preserves: the A-clear bit, the fact that gMarioState still points at Mario, and the fact that Mario's marioObj field still points away from Mario. (The same per-body walks that discharge §8 produce this.)
Hstore
censused single stores can't press A
A single assignment whose target provenance passed the census (it writes through a checked non-Mario pointer) cannot set the controller's A bit.
Hstoremwf
censused single stores preserve well-formedness
The same assignment cannot break any §7 row. (MWFReal already proves this for the harder in-engine store classes; this wrapper-level copy remains until the wrapper is retired.)

12 · The four run premises — obligations of the statement, not assumptions of the proof

These live inside the theorem statement: anyone applying the theorem to a concrete run must check them for that run. They are the theorem's honest scope, not gaps.

premiseplain meaning
P1 · mem_ok_lp … init The run starts sane: Mario's block exists; his action is outside T (standing on the ground — not already flying, not mid-cannon-shot); gMarioState points at him; his marioObj points away from him; and the §7 checklist holds. A checkable property of one concrete memory.
P2 · a_pressed_real = false, every frame The challenge condition itself: on every frame, following the controller pointer and reading buttonPressed finds the A bit clear (with "unreadable" counting as pressed — the premise can't be satisfied by corruption).
P3 · spawn_flying = false, every frame No frame's level script spawns Mario directly into a flying state (the warp/cutscene spawn path, which lives outside the frame function).
P4 · reachable … step_real The end state is actually reached from the start by real frames — each step is one big-step execution of the compiled execute_mario_action over the linked program.

14 · What is not on this page

Everything else is Qed. In particular, these used to be assumptions and no longer are: the per-frame value engine and its census walk over the 15 frame bodies of mario.c; the six semantic A-gate kills (dispatch, cannon fire, the three side-flip feeders, the landing-cancel indirect site, the button-update bridge); the taint-entry census (every entry into T in the linked sources is A-gated — a machine-checked enumeration); the input grounding ("A-silent frame ⇒ A-clear memory"); all 14 invariant obligations of MWF_real; the rest-surface decomposition and the stub body; the run induction; and "not-tainted implies not-flying."

Outside the formal system entirely (the extra-logical trust base, unchanged — see docs/trust-model.md): that the decompiled C source faithfully matches the shipped game; that clightgen faithfully translates C to the Clight AST the proof reads; that Clight's big-step semantics is the right meaning of that AST; that the one-frame-function-iterated model is the right frame model; and Coq's own kernel.

# Replacing Buddy: actor roles and actual delivery constraints

14 November 2026. **Buddy is not an ingredient required by Ink itself. He supplied a second, distinct sideways interaction in one successful conditional recipe.** The useful replacement must reproduce the required Mario movement and cache history, and it must have a real delivery history. A second ordinary grabbable item is not a direct substitute for Buddy in the same update: Mario processes only one collided object of each interaction type. The strongest distinct-type alternative to investigate is a nonmounting shell followed by one grabbable actor, with retuned geometry or timing. This source study does not establish that alternative's delivery or useful arrival.

This review starts from proof revision `1222ab0ee82b870ba5efe1a8afd7f3ea7e78b1bf`, branch `codex/ssl-pyramid-item-proof`, and decompile revision `36fbf8d693a9fc2bdec0c77402f8e96d07d2f461`. The applicable game version is original Japanese SM64. The audited interaction/action, shell/box, object-order, HOLP, behavior-script and SSL macro files have no diff against stock source pin `9921382a68bb0c865e5e45eb594d9c64db59b1af`. Existing disabled TAS-hack changes elsewhere are excluded. No new emulator run or Coq theorem is claimed by this note; the concurrent delivery and handoff experiments supply their own evidence.

## Why Buddy appeared in the earlier recipe

The [earlier useful three-actor test](ink-item-combination-verdict.md) supplies Mario in FREEFALL at Y1810. Shell contact plus Z enters a native slide at update128. At129, a Crazy Box and Buddy provide separate pushes; at130, a newly supplied Box position provides another push. The result has fresh cached floor768, movement/collision Y768 and stored graphics Y1830.177978515625. At131 the real warp accepts contact and the high stored-graphics retry captures the top; the demonstrated Area2 arrival is approximately `(365.59277,5500,-1096.80261)`.

Buddy's contribution is an X/Z push that preserves the required ground action. His NPC handler can do this when conversation is not accepted. It neither grants the ground action nor creates the vertical snap itself. His high placement, the Box's two placements and the initial Mario/shell setup were supplied. Removing Buddy from that unchanged recipe fails, but that comparison does not prove every successful recipe needs Buddy or two simultaneous pushes.

The [real acquisition follow-up](ink-buddy-acquisition.md) obtains Buddy's remembered conversation reference through A-off play, but the subsequent native pickup selects the Crazy Box instead. It does not hold or deliver Buddy. This motivates replacing the role rather than treating Buddy as an available carried item.

## The one-object-per-type restriction

`mario_get_collided_object` returns the first collision-list object whose current `oInteractType` equals the requested type. `mario_process_interactions` visits each handler type once and clears that type's bit before invoking the handler. A false return continues to the next **type**, not to a second object of the same type. Consequently:

- Crazy Box, small cork box and black Bob-omb all use GRABBABLE. Two such actors do not provide two independent grabbable pushes in one normal interaction pass.
- Buddy uses TEXT, which follows GRABBABLE, so the successful Box-then-Buddy combination can consume both types.
- A Koopa shell uses KOOPA_SHELL, which precedes GRABBABLE. Its fallback push can therefore compose with a later Box/Bob-omb/small-box push, if neither interaction takes an early terminating branch.
- Merely changing list order cannot make the same type execute twice. A clone also needs its actual retained interaction fields and history; it does not automatically gain a new interaction type.

Both collision detection and the later push matter. Detection records overlap against raw collision coordinates and the actor's actual hitbox. `push_mario_out_of_object` then uses Mario's current movement X/Z, wall-corrects the destination and commits only if a floor lookup succeeds there. It leaves the cached floor unchanged. A later push can read movement changed by an earlier handler; it does not rerun the original hitbox detection. Thus a supplied success at another actor radius or ordering is not automatically preserved by a simple name substitution.

## Same-update shell cancellation does not create a following shell

The proposed shortcut was: mount and press Z before the shell's first callback, leave its behavior in the following state, and then bring it to the pyramid while Mario walks, crawls or uses a Tweester. The actual status assignment prevents that first step.

1. Successful shell contact writes the ridden reference and an interaction status, then enters RIDING_SHELL_GROUND.
2. If Z is newly pressed in that update, `act_riding_shell_ground` calls `mario_stop_riding_object` before selecting CROUCH_SLIDE.
3. The stop helper **assigns** `INT_STATUS_STOP_RIDING` (`0x00400000`) to the shell's status and clears Mario's ridden reference. It does not OR that bit into the earlier status. `INT_STATUS_INTERACTED` (`0x00008000`) is therefore absent afterward.
4. PLAYER runs before LEVEL. When the still-action0 shell callback finally executes, its `INTERACTED` test is false, so it never increments to action1. It performs ordinary free-shell movement and clears the status.
5. Only action1 copies Mario's raw object position every update. That path was not entered. The surviving action0 shell stays free; it is not an actor that follows a now-unridden Mario.

If mounting instead survives a callback, the shell enters action1. A later Z cancellation sets STOP_RIDING, which action1 consumes by marking the shell for deletion. A normal Tweester contact also calls `mario_stop_riding_and_holding`, producing that stop signal for a genuinely ridden shell. Mounting a shell explicitly drops any normally held box/Bob-omb; it is not ordinary simultaneous item carrying.

A free shell can push a crawling or ground-sliding Mario when its nonmounting branch is reached. Walking/HOLD_WALKING contact or a qualifying hit from above remounts it instead. These interaction choices affect Mario; they do not provide a free-shell transport writer. Earlier supplied tests already record action0/free survival from same-update cancellation in [the slide handoff report](ink-slide-handoff.md); no duplicate new runtime claim is made here.

This closes the particular same-update-Z following-shell explanation. It is not an exhaustive no-shell-cloning theorem. Other action transitions, slot-reuse histories or initialization paths would need their own source and replay evidence. For example, `set_water_plunge_action` itself does not call the riding-stop helper, but that observation does not provide a usable SSL Area1 water-entry/exit history, a cleared ridden reference, or a high transported shell. It is not promoted to a gameplay candidate in this study.

## High delivery remains its own history

HOLP is updated by the held-object rendering callback. A high Mario position while holding nothing does not set a high HOLP. Preserving an earlier high HOLP off camera still requires an earlier real high held-object rendering and a later acquisition/release history that preserves it. Ordinary drop places actor Y at Mario's current movement Y; ordinary throw uses stored HOLP Y and offsets X/Z by32 in the facing direction. Native object callbacks and floor/wall processing continue afterward. These are real placement mechanisms, not an authorization to supply the hand position or actor coordinates.

Sources: [HOLP render callback](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/mario_misc.c#L547), [drop/throw coordinates](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/interaction.c#L295).

The next meaningful runtime comparisons are therefore (a) a genuinely acquired and carried small box or Bob-omb replacing the grabbable role with a new timeline, and (b) a genuinely released/free shell plus one grabbable actor with their actual order and positions. Each must connect the delivery history to fresh floor768, the productive slide/crawl code, accepted warp, top capture and retention, and displaced Area2 arrival. A successful substituted placement, even at an actor's normal dimensions, would remain conditional until that connection is replayed. This source review alone removes no delivery grant from the earlier useful handoff and does not change the open clean-route assessment.

## Focused carrying lead: alternate held walking and deceleration

A later focused review identifies a source-permitted way to climb some slippery slopes while holding an ordinary item: alternate one update of uphill stick with one update of neutral stick, keeping A/B/Z off. The intended cycle is **HOLD_WALKING → HOLD_DECELERATING → HOLD_WALKING**, not HOLD_IDLE. This is a concrete input proposal for the concurrent real small-box transport experiment, not a newly claimed replay result in this source note.

The relevant ordering is:

1. With no nonzero analog input or new A, `update_mario_inputs` sets `INPUT_UNKNOWN_5`. In HOLD_WALKING, that flag requests HOLD_DECELERATING before `update_walking_speed` runs.
2. HOLD_DECELERATING checks sliding first. In non-slide terrain, an uphill-facing Mario whose forward speed is above -1 does not satisfy `should_begin_sliding`, even when `INPUT_ABOVE_SLIDE` is set.
3. With neutral stick, `update_decelerating_speed` reduces forward speed toward zero by1 and updates horizontal velocity. Unlike ordinary walking, it does **not** apply slope acceleration. If the speed remains positive, the handler performs its ground step and remains HOLD_DECELERATING.
4. On the next uphill stick input, HOLD_DECELERATING again checks sliding, then requests HOLD_WALKING before its deceleration calculation. The moving-action initializer raises a nonnegative speed below `min(intendedMag,8)/2` to that amount. At intended magnitude at least8, this is4. The HOLD_WALKING case has no VERY_SLIPPERY exception; the ordinary WALKING case does.
5. The new HOLD_WALKING handler executes in the same action-dispatch loop, scales intended magnitude by0.4, updates walking speed and then performs the ground step. For full stick, a boost to4 is followed by forward acceleration `1.1 − 4/43`, then the uphill slope subtraction.

For a VERY_SLIPPERY slope, write `s = sqrt(normal.x² + normal.z²)`. With the stated full-stick and uphill guards, the illustrative real-number speed after the walking update is `q ≈ 4 + 1.1 − 4/43 − 5.3*s`. If `1 < q < 4`, the neutral update leaves `q−1 > 0`, and the next walking entry boosts it back to4. A 45-degree slope gives approximately1.2593 after walking and0.2593 after neutral: both updates retain positive uphill movement. The approximate sufficient inequality is `s < 0.75603`, or normalY above approximately0.6545 for a unit upward floor normal. This arithmetic describes the source lead; it is not a rounding-certified Coq bound, an exhaustive terrain result or a claim that every face near that threshold works.

The failure condition is also precise. If neutral deceleration reaches zero, it switches to HOLD_IDLE. HOLD_IDLE's common cancellation tests `INPUT_ABOVE_SLIDE` **before** nonzero analog input and selects HOLD_BEGIN_SLIDING. The player then loses this speed-reset cycle. Starting already HOLD_IDLE on such a slope also does not reach the proposed walking initialization directly. The test must therefore approach in held walking with enough positive speed and begin pulsing before it stalls.

Other premises remain actual gameplay obligations: keep facing uphill through the turning limit; use a non-Crazy-Box actor (Crazy Box immediately requests its bounce action in held idle/walking); preserve the item and valid ground contact; avoid stomp, squish, death, water and drop flags; and verify actual walls, changing floor normals, moving sand and step results. Ground-step loss enters HOLD_FREEFALL rather than proving successful climbing. This cycle uses stick transitions, not A edges, and preserves the held reference along the named normal branches. It may establish high actor/HOLP delivery if the runtime joins it to a genuine pickup and useful roof access; those endpoints are not supplied by the source calculation.

Sources: [holding speed initializer](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/mario.c#L896), [neutral input flag](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/mario.c#L1373), [walking and sliding tests](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/mario_actions_moving.c#L434), [held walking](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/mario_actions_moving.c#L875), [held deceleration](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/mario_actions_moving.c#L1134), [held idle cancellation order](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/mario_actions_stationary.c#L62).

Turning diagonally uphill does not reduce this walking speed subtraction on one unchanged floor face. `apply_slope_accel` selects the sign using the uphill/downhill half-plane and subtracts the full `5.3*s`; it does not project that subtraction by the cosine of the heading. A diagonal path might find a shallower neighboring face, but is not a way to repair the same face's `q <= 1` neutral-to-idle failure. This is a source restriction on the named pulse cycle, not an impossibility proof for carrying on every steep slope.

## Clone placement: establish and preserve real HOLP first

The user's intended clone strategy is relevant: establish an actual high held-object last position (HOLP), preserve it, acquire a fake object through a genuine slot-reuse history, then throw it at the stored hand position. That does not require physically walking the final enemy up the pyramid. This review does not replace that strategy with an assumption that every actor must be carried normally.

Two separate histories are required. First, Mario must really render a held object at the intended HOLP. The `GEO_CONTEXT_HELD_OBJ` branch of `geo_switch_mario_hand_grab_pos` records the transformed hand position after the renderer reaches a non-null held object with a non-null model child. Mario merely being high, or a high unheld actor existing nearby, does not run that setter. HOLP is full XYZ: Y1741 at a distant perimeter location does not deliver a clone at the Ink target's X/Z. A later low held-object render overwrites it. The ordinary object frustum test has depth and horizontal checks, so being vertically outside the visible screen alone is not a sufficient preservation argument.

Second, the acquired clone must have an actual lineage. Normal `act_picking_up` can finish its animation by grabbing the saved object reference without selecting a new GRABBABLE actor. This admits the known fake-object route if that selected donor disappears and a replacement occupies the same slot at the correct time. It is not a choice of an arbitrary existing actor pointer. The initial selection, destruction/unload, allocation order, initialization and completion of pickup must all occur in the replay. The clone must also avoid overwriting the intended HOLP before release.

For a real non-HOLDABLE actor, `obj_set_held_state` changes the behavior instruction pointer to the selected carry script and resets its stack index. `bhvCarrySomething3/4/5` each stop at `BREAK`; a fake-object pickup and release can therefore freeze the old native behavior while retaining its initialized interaction type, subtype and dimensions. A shell is interesting here because its KOOPA_SHELL type remains distinct from GRABBABLE, and its nonmounting fallback does not mark it INTERACTED. A frozen shell's source-level properties do not establish that its slot was actually acquired or that shell-plus-box geometry succeeds. A frozen Fly Guy retains BOUNCE_TOP and TWIRL_BOUNCE; freezing does not turn it into a neutral NPC push.

`mario_throw_held_object` uses HOLP XYZ with a32-unit facing-direction X/Z offset. `mario_drop_held_object` instead uses current movement Y, despite taking X/Z from HOLP. A native holdable item's thrown callback resumes its own movement, floor/wall checks and lifetime rules; a frozen non-HOLDABLE clone's carry script does not run that former callback. This makes actual clone placement different from native Crazy Box/Bob-omb placement, and both must be tested using the appropriate history.

A concrete high-HOLP source lead is a genuinely acquired Crazy Box. Its three bounce stages initialize upward speeds45,60,100 and minimum forward speeds32,36,48 without an A-edge test. It keeps the held reference during flight; the third landing clears it. In an unobstructed gravity4 profile, the positive ascent sums are276,480,1300 from each stage's own launch height. Thus a third bounce launched from a reached elevated floor could render the real held box high enough for the local1740-plus window. The required earlier landings, actual hand transform, useful X/Z and subsequent HOLP preservation are still missing gameplay obligations. These rises alone do not establish Y21778 or a VPU. The prior [air/actor review](ssl1-other-interaction-placement-review.md) already records the exact source profile; this is its relevance to HOLP, not a new runtime result.

The native shell's container is a SURFACE-list object, while a Bob-omb is DESTRUCTIVE. The container's action3 changes to action4 at timer7; action4 spawns the contents before its mist/triangle/sound children. This supplies a concrete allocation-order question for a fake-object shell experiment, not a ready-made clone: the donor must become available in time, no intervening allocation may take its slot, and pickup completion must reach the initialized shell. The locally instrumented exclamation-box source contains a disabled TAS-hack branch; the route claim must use the stock branch and the real controller history.

All three share `bhvFlyGuy`, nominal scale1.5, hitbox radius105/height90/down-offset0, BOUNCE_TOP and TWIRL_BOUNCE. Fire capability is a behavior-parameter choice, not a different neutral collision type. The macro coordinates and initialization commands are already covered by the existing [inventory](ssl1-clone-enemy-inventory.md) and its named generated-data checks.

The movement rules explain both genuine manipulation and its limits:

- `treat_far_home_as_mario(2000)` measures **three-dimensional** home distance. If the actor is farther than2000, it replaces angle-to-Mario with angle-to-home and distance-to-Mario with25000. If the actor is within its home sphere but Mario is outside that sphere, it sets the distance field to20000. These are steering substitutions, not a hard position clamp.
- Idle turns and enters approach when the substituted distance is at least25000 or below2000. Approach accelerates toward speed10 by0.5 and turns its movement yaw by at most0x200 per update. Otherwise it decelerates toward zero by0.2.
- In approach, facing within0x2000 and either being more than400 above Mario or having distance below400 permits an attack choice. Generic Fly Guy always lunges. Fire Fly Guy may instead shoot according to RNG. Lunge initializes speed25 projected into horizontal/vertical components, initially aims relative to Mario's Y minus200, and decelerates its downward component over roughly30 updates.
- The returning lunge phase spirals upward. While below `MarioY+200` it approaches upward speed20 by0.5; above that target it approaches zero by0.5 and waits for roll to settle before returning to approach. Therefore a new desired enemy altitude is not obtained by merely selecting X/Z. Mario's reachable height and the attack phase matter; upward momentum can overshoot the target, so200 is not a global maximum separation.
- The native callback still updates its state, velocity, yaw and small vertical oscillation while FAR_AWAY. `cur_obj_move_standard` skips ordinary displacement in that condition. Carefully changing activation can therefore separate state changes from normal movement. The home-return sphere is not a proof that manipulation beyond it is impossible. This also is not proof that arbitrary Y21778/VPU placements can be reached.
- Active standard movement checks walls, floor availability, slope entry and water. It refuses intended X/Z with a floor below `FLOOR_LOWER_LIMIT_MISC`; being a flying enemy does not bypass these checks. The relevant path does not perform a conventional ceiling query. Its raw position, home, activation distance and Mario target do not become VPU-equivalent just because a terrain query aliases.

At X/Z `(-1950,-939)`, the geometric upper surface of the western actor's2000-radius home sphere is aboutY2525.55. This is a **steering-region calculation**, not a tested maximum height or a reachable interval. Both the actor and Mario positions used for chasing, exact attack phase and actual terrain must still be reached. It gives a reason to test local-height luring first; it supplies no21,778–32,767 or +65,536 actor-delivery witness.

| --- | --- | --- |
| Qualifying falling hit from above | Movement Y snaps to actorY+hitboxHeight, vertical speed80, then `drop_and_set_mario_action(..., ACT_TWIRLING,0)`; interaction returns true | A useful no-A height source in another route, but changes the ground action, releases held/ridden objects and stops later interaction handlers. |
| Vulnerable ordinary side contact | Damage and knockback action; returns true | Does not preserve crawl/butt slide and does not call the NPC-style positional push. |
| Side contact while the damage guard rejects it | No damage transition; handler eventually returns false | Ignoring damage does not add a sideways separation push. |
| Successful punch/kick/trip | Attack status plus backward velocity recoil; ordinary grounded recoil is-48 | This is velocity/action processing, not an immediate X/Z shove with the old floor cache. |
| Qualifying fast slide/shell attack | Attack status; no neutral X/Z separation writer | Can retain a ground action in this branch but does not perform Buddy's needed shove. The native health-zero enemy is then removed by its attack callback. |

`interact_bounce_top` contains no call to `push_mario_out_of_object`. A frozen clone preserves that fact and the twirl subtype; it also loses the normal callback that clears its interaction status. Changing its location alone cannot convert these branches into NPC collision. The separate Fire Fly Guy projectile uses FLAME: it selects burning jump/fall and terminates that interaction, with the guards and launch already documented in [the other-interaction review](ssl1-other-interaction-placement-review.md). Burning-ground movement can be relevant to climbing, but it is reached after the burn's air/landing history and its handler does not call the common slide's `align_with_floor`. None of these observations rules out an earlier Fly Guy assist followed by a different successful producer update.

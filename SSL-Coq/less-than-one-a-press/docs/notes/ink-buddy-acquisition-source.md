# Can gameplay select the SSL cannon Buddy for pickup?

14 November 2026. **The ordinary pickup, conversation and in-area fake-object paths reviewed here do not acquire the native pink Bob-omb Buddy. Talking can legitimately make him Mario's remembered `usedObj`, but the next normal pickup selects its grabbable target again. A pending pickup cannot have its remembered target replaced by Buddy's conversation callback.** No new controller route that holds or delivers Buddy is established by this source audit. This is a closure of specified stock paths, not a machine-checked theorem about every original-ROM history.

This study starts at proof commit `49807c387f90e29856e2ae34a656f9394137ec19`, branch `codex/ssl-pyramid-item-proof`, and local decompile commit `36fbf8d693a9fc2bdec0c77402f8e96d07d2f461`. The game version is original Japanese SM64. A scoped `git diff --name-only` against stock source pin `9921382a68bb0c865e5e45eb594d9c64db59b1af` returned no changed files for the interaction, Mario/action, object-list, Buddy, object-helper/physics, behavior interpreter, macro-loader, behavior-script, macro-preset and SSL macro files audited below. Existing disabled `SSL_SPAWNING_DISPLACEMENT_TAS_HACK` edits in other files are excluded. This note contains source analysis, not a new emulator replay or proof build.

The [earlier movement audit](ink-buddy-movement-source.md) already established that Buddy is not unconditionally immovable: actual generic drop/throw code can relocate an already-held Buddy. Its [runtime record](ink-buddy-movement-runtime.md) deliberately supplied the missing pickup pointer. That experiment is not repeated or counted as gameplay here. The [acquisition research](ink-buddy-acquisition-research.md) records external cloning precedents and their limits. The new controller experiment is recorded separately in the acquisition instrumentation; its runtime evidence must not be inferred from the source arguments below.

## Three different pointers

`interactObj` is the object selected by a current interaction. `usedObj` is an object remembered for an action, including conversations, warps and pickups. `heldObj` is the held item. The source census finds one direct non-null assignment to Mario's `heldObj`: `mario_grab_used_object` copies `usedObj` when `heldObj` is null, then calls the held-state helper. It does not itself test the actor's species or interaction type. That permissive helper is why a supplied pointer succeeds, but reaching its call with the right pointer is the gameplay problem.

The SSL actor is the Area 1 macro `macro_bobomb_buddy_opens_cannon_1` at `(-5990, 0, -3871)`. Its native script is `bhvBobombBuddyOpensCannon`, with `INTERACT_TEXT`, `INT_SUBTYPE_NPC`, and `OBJ_FLAG_HOLDABLE`. HOLDABLE controls handling after selection; it is not the GRABBABLE interaction type. Buddy's native idle/turn/talk callbacks do not change him to GRABBABLE.

Sources: [generic held assignment](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/interaction.c#L288), [native Buddy script](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/data/behavior_data.c#L3777), [Buddy initialization and actions](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/behaviors/bobomb.inc.c#L292), [SSL placement](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/levels/ssl/areas/1/macro.inc.c#L12).

## All five calls to the generic grab helper

| Caller | Actual selection and timing | Why the native TEXT Buddy is not obtained |
| --- | --- | --- |
| `act_dive` | Calls `mario_check_object_grab`; on success immediately calls the generic grab helper before the air step. | The current grabbable interaction flag/target is required; the selector first copies `interactObj` to `usedObj`. An old conversation target is replaced. |
| `act_dive_slide` | Can first cancel to rollout, or change to the slide-stop action. If it reaches a successful `mario_check_object_grab`, it immediately calls the generic grab helper. | The same fresh-target requirement applies even when the preceding slide-stop transition makes the selector choose ordinary PICKING_UP. |
| `act_picking_up` | When action state is zero and the animation ends, calls the helper without reselecting. Stomp/off-floor checks precede it; common object-action water/squish/death/quicksand checks also run first. | This really permits delayed fake-object pickup. Its only named action-entry setter first remembers the selected GRABBABLE object. Buddy conversation cannot replace that pointer while pickup remains pending; Buddy must instead become the actor in the remembered slot, or another actual source path must be shown. |
| `act_picking_up_bowser` | Calls the helper at action state zero on the first execution of this handler. Its sole named entry is the Bowser branch of the selector, which writes `usedObj = interactObj`. | Bowser is not a native SSL actor. The remembered selector target must have Bowser behavior. Pending Bowser pickup also belongs to the OBJECT action group and cannot receive the Buddy dialog overwrite. First handler execution need not occur in the selector's update. |
| `check_water_grab` | Directly finds a collided object whose type equals GRABBABLE, checks facing, writes `usedObj`, then immediately calls the helper. | This bypasses some ordinary pickup restrictions, explaining water pickup of a Heave Ho, but does not bypass the GRABBABLE type requirement. Buddy remains TEXT. |

`ACT_DIVE_PICKING_UP` is not a sixth grab call. Dive/dive-slide already acquired the held object before entering it. Landing while holding after a dive and ending a held stomach slide can also enter this action. Its off-floor/slope exits explain hands-free holding of an existing item; they do not acquire Buddy.

For ordinary selection, `able_to_grab_object` accepts DIVE/DIVE_SLIDE unless the target grabs Mario, or PUNCHING/MOVE_PUNCHING with `actionArg < 2`. The grabbable handler also rejects the NOT_GRABBABLE subtype and distinguishes attack/being-grabbed branches. The non-Bowser selector requires facing within inclusive `[-0x2AAA, +0x2AAA]`; Bowser uses inclusive `[-0x5555, +0x5555]` relative yaw. The early punch sequence calls that selector only when its animation frame is at least two. These conditions are distinct from the generic helper's lack of a species check.

## Why an edge transition does not swap the target

The early-punch/ledge/dive mechanism used for light grabbing deserves an ordering check: a flag can survive an action change inside one update. It does not survive as an old target into arbitrary later updates.

1. `update_mario_inputs` begins each Mario update with `m->input = 0`.
2. Mario then processes special floors and object interactions once, before the action-execution loop.
3. The successful GRABBABLE handler writes `interactObj`, sets `INPUT_INTERACT_OBJ_GRABBABLE`, and returns true. The interaction loop breaks. GRABBABLE precedes TEXT, so Buddy's TEXT handler cannot subsequently replace `interactObj` during that interaction pass.
4. Action changes can loop within Mario's update. No other object's behavior callback or second interaction pass runs between those action handlers. An edge departure can therefore carry the donor's flag into a dive, but the dive selector still remembers that donor before the adjacent grab.
5. Buddy belongs to GENACTOR, which is updated after PLAYER. Its later native dialog callback cannot interleave with Mario's action loop. On the following Mario update, input flags are cleared again.

Thus the source mechanism behind light grabbing does not by itself provide a way to use a grabbable donor's flag together with Buddy's conversation target. This is a source deduction, not a failed finite search dressed as a general statement about cloning.

Sources: [fresh input flags](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/mario.c#L1373), [Mario update order and action loop](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/mario.c#L1699), [interaction priority](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/interaction.c#L84), [break on successful interaction](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/interaction.c#L1780), [object update order](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/object_list_processor.c#L172).

## Conversation creates a real reference, but consumes the pickup opportunity

Original JP NPC contact uses a new B input. With an idle-flag action or WALKING and facing Buddy within inclusive `[-0x4000, +0x4000]`, `check_npc_talk` writes both `interactObj` and `usedObj` to Buddy, pushes Mario and changes action to WAITING_FOR_DIALOG. This is a legitimate no-new-A predecessor. It does not call the grab helper.

The later `set_mario_npc_dialog` callback can also write `usedObj = gCurrentObject`, but only when Mario is ready to speak; it simultaneously changes his action to READING_NPC_DIALOG. Ready means WAITING_FOR_DIALOG or the STATIONARY/MOVING groups, excluding shell riding, invulnerability and first person. PICKING_UP (`0x383`), DIVE_PICKING_UP (`0x385`) and PICKING_UP_BOWSER (`0x390`) are OBJECT-group actions, so the new-dialog branch rejects them. The special already-in-dialog branch checks the *current* READING_NPC_DIALOG action, not just a retained Buddy dialog variable; it does not write the used pointer or restore an old pickup.

Dialog completion selects putting-on-cap, IDLE or HOLD_IDLE according to actual state. It never resumes a pre-dialog PICKING_UP. Conversely, entering another normal pickup after talking overwrites the remembered Buddy with that pickup's selected donor. If an interaction cancels pending pickup into a talk-compatible action, subsequent dialogue does not preserve the canceled pickup as a hidden continuation.

The earlier [generated-code proof](ink-buddy-movement-proof.md) establishes the three named pickup actions' false `mario_ready_to_speak` result. That helper theorem supports this branch closure; it is not a theorem that every reachable history has the required action/pointer invariant.

Sources: [JP B-only NPC path](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/interaction.c#L1669), [readiness and dialog writer](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/mario_actions_cutscene.c#L324), [dialog completion](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/mario_actions_cutscene.c#L377).

## Other writers and fake-object replacement

The direct Mario `usedObj` writer census includes pickup selection; star/key, BBH entrance, warp/warp-door/door, cannon, igloo barrier, tornado, whirlpool, wind, shell, grabbed-by-object, pole, Hoot, sign and NPC interactions; water grab; NPC callback; warp initialization; and Mario initialization. Camera `usedObj` fields are separate storage. None supplies a second ordinary held-object assignment.

Most interaction writers change Mario's action. The igloo barrier is a real exception: it remembers the barrier without changing action. The review must not replace this fact with an assertion that every non-pickup writer cancels pickup. However, it selects the barrier's interaction type, not TEXT, and the stock SSL area has no igloo barrier. A native Buddy still cannot be its target under the actual exact-type collision selection. The same type distinction excludes Buddy as the target of the other non-TEXT interaction writers. For this actor, the only normal in-area writers that can install his pointer are therefore the two conversation paths examined above.

Delayed pickup's slot-replacement behavior is real and explicitly described by the source. To clone Buddy by that mechanism, a remembered donor slot must become a live Buddy before the delayed grab. The already-live native Buddy has his own occupied slot; removing a different donor does not transfer Buddy into it. The reviewed source has no in-area native `spawn_object` call naming either Buddy behavior. The SSL macro entry creates him through the area loader. Generic parameterized spawning is why this textual constructor census alone is not a complete semantic theorem.

Walking beyond his display distance does not reload him. `set_object_visibility(..., 3000)` changes an invisible render flag; the behavior interpreter's distance check changes rendering and FAR_AWAY. Neither frees the object slot. `OBJ_FLAG_PERSISTENT_RESPAWN` concerns whether unloading marks the macro as suppressed on later area entry; it is not a near/far respawner. Buddy's own callback and `object_step` contain no deactivate/delete path.

Ordinary area exit/re-entry loads objects again but also runs Mario initialization, clearing held/used pointers and selecting a spawn action. The same-area fading-warp pair also uses `init_mario_after_warp`; it does not preserve a pending pickup. SSL Area 1 has no instant-warp table. The Area 2/3 instant-warps do not furnish a Buddy reload into a pending Area 1 pickup. These are the normal reload paths reviewed, not a claim about every possible malformed area state.

## Exact source-induction boundary

A useful conditional whole-history statement would fix a native live Buddy slot `B` and require:

- Begin at a complete update boundary with `heldObj != B` and no pending ordinary/Bowser pickup already targeting `B`; an intermediate starting cut must additionally establish its current grab-flag/target provenance. An arbitrary mid-update flag and target are not an allowed initial history.
- While the area remains loaded, `B` stays allocated to this Buddy, retains native TEXT/NPC behavior and is not reused as a donor slot.
- Collision records and their selected objects have the provenance supplied by the game's collision pass; Mario inputs, action transitions, pointer writers, object scheduling and resets follow the audited JP code.
- On normal area reload, the actual Mario initialization/reset and Buddy construction are included before restarting the argument.

Then a first acquisition of `B` cannot arise from any of the five callers: immediate selectors choose another interaction type; pending pickup entered with another target cannot receive a Buddy conversation overwrite while remaining pending; cancellation does not resume the old pickup; and another held/donor slot cannot turn into the still-live slot `B`. This source induction does not depend on forbidding A, so within those premises it also covers no-new-A play. It covers acquiring this native actor, not an unconditional statement that no cloned actor of any lineage can ever resemble him or move like him.

The remaining proof obligations are the **integrated** slot/type lifetime, collision provenance, exhaustive reachable behavior construction and action/initialization invariants. A grep census and helper proofs do not discharge them. No alternative stock writer was found in this audit; the unproved part is connecting the reviewed branch arguments into that full execution invariant, rather than a demonstrated reachable bypass.

For gameplay progress, the closest useful predecessor is a naturally obtained `usedObj = Buddy` after B conversation with `heldObj = NULL`. Its first failed condition is reaching a real generic grab call while that same remembered target remains Buddy. An ordinary donor pickup is a discriminating control because it should show the target overwritten before the delayed grab. Further search should identify a concrete in-area Buddy-construction/slot-replacement path or an actual pointer-preserving action transition missing from this census before repeating broad pickup-button scans. If no such path exists, direct terrain movement of the native Buddy is a separate actor-delivery question, not evidence of grabbing or cloning him.

No supplied Mario state, object position, pickup pointer, input flag, collision list or action is used as a positive witness in this note. No new Coq claim or original-ROM replay is asserted here.

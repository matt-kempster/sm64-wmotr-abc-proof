## HeldObj, hands-free teleporting and the meaning of same-area

The end-to-end held-pointer claim remains **open**. The actual initializer
reset is checked, but neither null preservation to the first displacement
nor all relevant successful warp continuations have been proved. No reachable
nonnull-heldObj arrival in SSL Area 2 has been established. In particular,
the results below must not be labeled a completed no-item theorem.

The user's hands-free objection exposes another necessary distinction.
[Hands-free teleport](https://www.youtube.com/watch?v=qqmYYIQRSuI) is a documented
gameplay trick; the [reported object effects](https://www.mariowiki.com/List_of_Super_Mario_64_glitches#Hands-free_teleport)
include invisible objects and Bob-ombs that can be grabbed again after
teleporting. This is evidence about ordinary hands-free teleportation, not
a demonstrated Teleporter Wrong Warp carrying an object into SSL Area 2.

MarioState's `heldObj` and the object's own `oHeldState` are different cells.
The generated hold helper sets `rawData.asU32[39]` to 1 (`HELD_HELD`). The
checked layout places this word at object offset 292, or `0x124`; Mario's
held-pointer field is at MarioState offset 124, or `0x7C`. The new
`TeleporterHeldObjectState.v` consumes the actual held-pointer reset and
proves that it preserves this object-state word when the object and
MarioState occupy distinct blocks. In particular, Mario's pointer becomes
null while an incoming object held-state value of 1 remains 1 at that same
reset checkpoint. This is local retention, not a constructed whole-warp run.

The stock Bob-omb dispatcher switches on its own held state. Its held loop
hides the object and calls `cur_obj_set_pos_relative(gMarioObject, 0, 60, 100)`
without consulting Mario's `heldObj`. The new source certificate checks its
held-loop/follow calls and the absence of a `heldObj` reference in that loop;
it does not execute the complete Bob-omb behavior. Bob-omb behavior normally
runs in list 2 after scheduled platform displacement. Thus hands-free
following does not by itself contradict null **at the first apply**, but it
does show why even a finished pointer theorem would not exclude all later
item effects. A useful route additionally needs the object's lifetime,
area activation, behavior and interaction history.

An ordinary **same-area teleporter** and the internal warp type
`WARP_TYPE_SAME_AREA` must also be distinguished. The generated `initiate_warp`
chooses change-level for credits nodes or a different level, change-area for

The comparison is with the current area when classification runs. Merely

documented [Teleporter Wrong Warp](https://ukikipedia.net/wiki/Teleporter_wrong_warp)
starts with an area change during teleportation, so its usual teleporter's
destination does not authenticate the final internal type or continuation.
No emulator analysis was resumed to close that separate gap.

`gMarioPlatform` is a cached **object address**. With a nonnull Mario Object,
the end-update `update_mario_platform` queries the floor at its collision
position. When Mario is less than four units from that floor and the floor
has a nonnull object owner, it remembers that owner. Otherwise it clears the
platform references. The next object update moves terrain first, then applies
movement from the remembered address to Mario, and only later checks support
again. This ordering normally lets Mario ride a moving platform.
If Mario Object is null, the updater returns without clearing the references;
the displacement dispatcher also requires Mario Object to be nonnull.

| Pointer | What it records | Relevant consumer |
|---|---|---|
| `MarioState.heldObj` | The object Mario is holding. | Held-object actions and interactions. |
| `gMarioObject->platform` | Object-side platform bookkeeping. | Object/platform bookkeeping. |
| `gMarioPlatform` | Cached support-object address. | The early Mario displacement dispatcher. |

The dispatcher checks time stop, Mario's existence and a nonnull cached
pointer. It does not revalidate the object's activity, floor ownership,
behavior or logical lifetime at that point. It reads the current horizontal
velocity and rotation/pivot fields at the address. If an object unloads and
its fixed pool slot is reused, the address can remain the same while those
fields belong to a different object. This is the source of the object-lifetime
problem behind spawning displacement; it need not require an invalid memory
access.

**Could it help a route? Mechanically, yes.** A surviving pointer with useful
movement fields can displace Mario even after his position has been reset.
The existing supplied Ink controls demonstrate conditional displacement
payoffs. They do not supply a reachable Teleporter Wrong Warp or same-area
setup. A nonnull pointer with zero or unsuitable movement is not enough, and
an unproved null invariant does not create an in-game pointer.
Retaining this support pointer also does not by itself restore `heldObj` or
give Mario an item he can carry or throw.

"Preservation" has a precise meaning here: the memory cell holding the
address keeps its value through a specified execution interval. Preserving
null would prevent this dispatcher from moving Mario. Preserving a nonnull
address might retain a setup, but does not prove the object's identity or
contents remain unchanged. Those are additional lifetime and payload facts.

For a reachable same-area candidate, the incoming pointer must be explained
at the last source-frame capture. Merely riding a useful platform much
earlier does not keep it: the teleport fade continues its normal floor snap
and end-update recapture. A valid history needs support near the relevant
time, a justified disagreement between Mario's movement and collision
samples, or a precise unload/reuse opportunity. No such clean SSL-2 history
has been established here. An injected pointer is only a downstream test.

The normal-frame source order is:

`warp_area → check_instant_warp → area_update_objects → terrain updates → first scheduled platform apply → other objects/Mario → unload → final support capture`.

Therefore the destination's final support capture is too late to protect
that first apply. The initialization, intervening instant-warp check and

## Reset and displacement order

For a successful ordinary warp with a valid spawn object and Mario's action
different from `ACT_UNINITIALIZED`, the relevant source sequence is:

1. `initiate_delayed_warp` looks up `sSourceWarpNodeId` in the **current**
   area's warp list, then reads its destination without a null check
   (`src/game/level_update.c:819-883`; lookup at 873). The lookup itself can
   return null (`src/game/area.c:149-158`). A null dereference supplies no
   normal CompCert execution that produces the Virtual Console stale
   registers.
2. `warp_area` unloads/loads the area for `WARP_TYPE_CHANGE_AREA`, then calls
   `init_mario_after_warp`; `warp_level` loads the destination area and calls
   the same initializer (`src/game/level_update.c:463-487`).
3. For either change-area or change-level, `init_mario_after_warp` sets the
   destination spawn-area index and calls `load_mario_area`, then
   `init_mario`, then `set_mario_initial_action`
   (`src/game/level_update.c:367-393`, especially 384-390).
4. `load_mario_area` calls `spawn_objects_from_info(0, gMarioSpawnInfo)` when
   the loaded area matches the spawn area (`src/game/area.c:261-268`). This
   Mario-spawn call does not depend on a nonempty area object-spawn list.
5. Before its allocation loop, `spawn_objects_from_info` calls
   `clear_mario_platform` under `#ifndef VERSION_JP`
   (`src/game/object_list_processor.c:453-465`). The latter is exactly a null
   assignment to `gMarioPlatform`
   (`src/game/platform_displacement.c:179-185`). Therefore this source path
   clears the retained platform in US, PAL/EU and Shindou; original JP lacks
   that reset. Only US/JP instances are presently generated in this project.
6. On the destination normal frame, `play_mode_normal` performs `warp_area`
   before `area_update_objects` (`src/game/level_update.c:962-981`).
   `update_objects` updates terrain objects, applies Mario's platform
   displacement, and only later recaptures Mario's platform
   (`src/game/object_list_processor.c:646-670`). The only direct caller of
   `update_mario_platform` in the pinned C source is that final call.

Consequently the ordinary **non-JP** destination-load sequence has a source
argument against displacement inherited from the source area's retained

(`src/game/platform_displacement.c:171-176`). This is the relevant argument

The exported `shindou_reset_instruction_boundary_checked` also proves the

### Area-change candidates, without a reachability claim

The straightforward reported mechanism requires an area change while the
teleport is pending. The only stock areas containing both a fading-teleporter
declaration and a same-area `INSTANT_WARP` declaration are:

- **SSL Area 2:** instant index 3 goes to Area 3 with zero displacement
  (`levels/ssl/script.c:128`). Area 3's instant index 2 returns to Area 2
  (`:141`). Area 3's object-warp table has only success/death nodes, so it
  does not supply teleporter source IDs `0x15` or `0x16` (`:135-137`).
- **WDW Area 1:** instant index 1 goes to Area 2 with zero displacement
  (`levels/wdw/script.c:106`); Area 2's index 0 returns to Area 1 (`:118`).
  Area 2 has only success/death object-warp nodes (`:116-117`), so it does
  not supply source IDs `0x0B` or `0x0C`.

For the direct SSL-2-to-SSL-3 candidate with the delayed lookup still
occurring in Area 3, a supposed destination of SSL Area 2 is necessarily a
change-area destination: `initiate_warp` compares the destination area against
`gCurrentArea->index` (`src/game/level_update.c:615-629`). That particular
continuation takes the platform-reset branch. If Mario instead returns to
Area 2 before lookup while preserving stock source IDs `0x15`/`0x16`, their
nodes are present there and this missing-node trigger is absent. Neither
observation excludes schedules with altered captured IDs or another cause
of corruption.

This intersection is a useful search reduction, not proof that both setups
are physically achievable or that these are the only possible wrong-warp
origins. CCM Area 1, LLL Area 1, SL Area 1, THI Area 2 and TTM Area 1 are
teleporter areas in multi-area levels, but they have no local instant-warp
declaration. TTM's slide instant warps are in Areas 2 and 3, separately from
its Area-1 teleporters (`levels/ttm/script.c:154,165`). DDD and the castle have
instant transitions but no stock fading-teleporter declaration.

`check_instant_warp` reads Mario's floor and changes area before the normal
object update (`src/game/level_update.c:530-567,974-975`); it has no teleport
action exclusion. This makes the two intersections relevant. It does not
prove the timing or geometry needed to reach those floors while teleporting.
Ordinary object interactions are gated by `ACT_FLAG_INTANGIBLE`
(`src/game/interaction.c:1784`), which is set in the teleport actions' action
constants (`include/sm64.h:380-381`). Hence ordinary area-changing object
warps cannot simply be assumed available throughout the fade. Painting entry
also rejects intangible actions (`src/game/level_update.c:664`). Script,
action-cancellation, platform-motion and corruption alternatives require
their own execution analysis.

### Source-ID provenance and the Shindou register argument

The inventory's distinct source IDs are exactly
`{0x0B, 0x0C, 0x0D, 0x0E, 0x15, 0x16, 0x1F, 0x20}`. None is `0x08` or
`0x88`; SSL's level ID is `0x08` (the `LevelNum` enum expansion in
`include/level_table.h:7-13`, with SSL as the eighth entry in
`levels/level_defines.h:20-27`). Therefore a
machine-level result saying that the wrong destination level equals the
original teleporter's source ID masked by `0x7F` would exclude SSL for these
stock IDs. Authenticating that result, its Virtual Console fault semantics,
and its source-ID premise is separate work; the inventory alone does not
establish it.

Source-ID capture is later than teleporter activation. `interact_warp` sets
`usedObj` when entering the fade, but `act_teleport_fade_out` waits until
`actionTimer` reaches 20 to call `level_trigger_warp`
(`src/game/mario_actions_cutscene.c:1395-1416`). Only then does the teleport
case read the second parameter byte of `usedObj` into `sSourceWarpNodeId`
(`src/game/level_update.c:769-772`). An earlier area change could unload or
reuse the object slot to which `usedObj` points. A stock-ID theorem must
therefore justify the parameter byte at the capture point, not merely cite
the object activated 20 frames earlier.

The follow-up found a concrete reason this premise matters: the SSL Area-2
Goomba triplet spawner creates children with second behavior-parameter bytes
4, 8 and 16. Thus a stale/reused slot cannot be dismissed using the teleporter
inventory's IDs alone. No reachable slot-reuse schedule is proved here.

The capture case also immediately calls `music_changed_through_warp` with
the captured ID (`src/game/level_update.c:772`). That helper performs its
own unchecked warp-node destination reads (`:567-599`). An area change before
capture could therefore encounter invalid reads before reaching the eventual
delayed-warp suffix. A certificate for only that final suffix cannot silently
cover this earlier-fault variant.

After capture, every source-level assignment to `sSourceWarpNodeId` is in
`level_trigger_warp` (`src/game/level_update.c:710-786`), beneath its
`sDelayedWarpOp == WARP_OP_NONE` gate at 702. `check_instant_warp` and
`change_area` do not reset that gate or the latched source ID. Thus an ordinary
instant area change during an already-pending delayed warp does not itself
replace the latched ID. Extending this source observation through a particular
complete run, including exceptional or corrupted states, remains an execution
obligation.

## Formal result and integration

`TeleporterWrongWarpBoundary.v` reads the committed generated US/JP ASTs.
Its checked boundary identifies the four-action fading-teleporter gate,
the first destination read in both the delayed-warp path and the earlier
music check, the held-object reset assignment, and the US spawn-prefix
platform-clear call (absent in JP). It proves that the identified null-node
reads have no `Clight.step2` successor. It also proves the immediate null
store/load postcondition of executing the actual generated platform-clear
statement, including resolution of the global symbol's memory block. This
does not prove preservation through later callbacks or arrival at that
statement in an emulator execution.

`MainTheorem.current_teleporter_wrong_warp_boundary` consumes that boundary
and `TeleporterShindouReset.shindou_reset_instruction_boundary_checked`.
Both new modules are registered in `_CoqProject`. The capstone is deliberately
a conjunction of these concrete evidence boundaries, not the requested
all-origin VC impossibility statement and not a discharged premise of the
whole-run no-star theorem. The advance is narrower: the reset instructions,
source paths and source/machine semantic gap are now explicit checked objects
instead of an unspecified altered-warp possibility. The held-item gameplay
invariant, source-ID capture provenance, emulator transition and first-apply
preservation remain separate obligations.

## What remains to settle the requested claim

The current authorized scope is the source-level alternative described in the
handoff: prove an invariant for every relevant valid destination continuation,
with same-area paths and preservation through the first apply made explicit.
That could avoid enumerating every controller history, but only if the
coverage argument is proved. The supplied images and local
execution certificates do not by themselves provide that coverage. The
machine/emulator bridge remains unresolved and is no longer being pursued.

A disproof still requires a clean reachable setup retaining an item at the
stated control point or producing the specified spawning displacement; an
injected pointer/register fixture would establish only a downstream effect.
The activation interpretation, successful-origin classification and
whole-game invariant remain open. The new source boundary consumes four local
execution modules; neither it nor the unchanged earlier VC evidence boundary
asserts the universal gameplay result.

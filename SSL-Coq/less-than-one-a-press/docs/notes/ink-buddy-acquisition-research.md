# External predecessor search for acquiring the SSL cannon Buddy

14 November 2026. **This search found no verified original-JP gameplay history that grabs or clones SSL Area 1's pink Bob-omb Buddy without a new A press.** It found relevant original explanations of fake-object pickup, interference cloning, transport cloning and HOLP preservation. None of the inspected descriptions supplies the missing step: getting the already-spawned SSL Buddy into Mario's held object reference. This is a report of what was found, not a proof that no such history exists.

The research began from proof checkout `49807c387f90e29856e2ae34a656f9394137ec19`, branch `codex/ssl-pyramid-item-proof`. The [existing source audit](ink-buddy-movement-source.md) and [conditional movement experiment](ink-buddy-movement.md) were read first. Their source pin is `9921382a68bb0c865e5e45eb594d9c64db59b1af`, with decompile checkout `36fbf8d693a9fc2bdec0c77402f8e96d07d2f461`. The previous experiment's explicit `usedObj` retarget is excluded from the present gameplay acquisition request.

## How these precedents bear on the actual obstruction

The important distinction is that a cloning setup can make Mario remember a vacant **slot**, but it does not let the player choose an arbitrary live object's address. The source audit at the starting revision records a native Buddy body loaded from the Area 1 macro entry, with TEXT/NPC interaction and persistent GENACTOR membership. That body has no known in-area respawner. Hiding it is not freeing its slot. A proposed fake-box/Bob-omb route therefore needs an actual allocation or pointer-writing event that selects Buddy; merely improving the donor's vacant-slot index does not establish that event. These are source-audit statements, not deductions from the absence of a search result. See the [source record's pickup and loading analysis](ink-buddy-movement-source.md).

Likewise, transport cloning needs an actual object-collision pair and a reached position-writing callback. The prior source audit specifically checks the two-body resolver and its stock callers; it does not assume the resolver moves only one participant. It finds that the relevant stock enemy/list pairings do not register a direct Goomba/Buddy pair. A new transport proposal must name a reachable actor/list lineage that changes this condition. The original transport-clone description supplies no such Buddy lineage.

The [existing movement experiment](ink-buddy-movement.md) does establish a useful conditional fact: after a deliberately supplied pickup-reference retarget, ordinary drop/throw code can move Buddy. That is why searching for real acquisition is meaningful. It does not fill the acquisition gap, and it is not a predecessor that this task can accept unchanged.

## False positives excluded

- [James S' Kingdom's pickup codes](https://sites.google.com/site/jamesskingdom/Home/game-codes-by-james-s/super-mario-64-codes/sm64-pick-up-codes) explicitly advertises a code for picking up Bob-omb Buddies. It is a cheat-code result, not a gameplay route.
- The historical [Chuckya Glitches forum thread](https://gamefaqs.gamespot.com/boards/198848-super-mario-64/44114606) contains a first-person claim about cloning a pink object covering a cannon in Wet-Dry World. The wording does not reliably distinguish Buddy from a cannon-related object; the described preparation also includes A input. No corresponding movie or SSL transfer was verified. It is not evidence for this request.
- Broad descriptions saying that almost any object can be cloned omit the needed loading and pointer-history conditions. Claims about a visible duplicate, an arbitrary held address, a changed behavior, or a ROM hack were not promoted into native actor delivery.
- The existence of a HOLP-preserving technique concerns **where a later release can write coordinates**. It does not by itself establish **which object Mario has acquired**. Similarly, a terrain query alias at a VPU height does not relocate Buddy's raw object coordinates.

## Checks suggested by the references and their current disposition

1. The stale grab-authorization and action-redispatch proposal was sent to the concurrent source audit and checked as described above. A different positive candidate must identify the actual native pointer-writing event that bypasses those reviewed guards; the light-grab analogy alone no longer supplies an untested opening.
2. For any fake-object attempt, log donor destruction, free-list order and the **constructor of the replacement object**. Stop calling it a Buddy route if the held slot is only vacant or contains another actor. A no-A fake pickup would still be a useful reproducible predecessor for other SSL clone routes.
3. If a loading-boundary proposal is raised, distinguish an instant area change that preserves a held reference from the ordinary SSL warp/reinitialization path. Require a native return to Area 1 with a Buddy allocation in the retained slot, rather than borrowing a Wet-Dry World example without its loading-zone semantics.
4. Only after a legitimate acquisition has been observed should a high-HOLP delivery search be credited as Buddy transport. Its output needs Buddy's raw XYZ at the producer cut, the native action/held-state history, and the subsequent useful Area 2 spawning displacement. The earlier conditional release experiment is an appropriate control for that later stage.

No ROM replay, Wafel experiment, Coq theorem or controller witness is produced by this external-research note itself. The local source and runtime investigations are the appropriate places to settle the concrete leads above. The external search leaves the gameplay question open and adds no counterexample to the no-new-A route assessment.

# Choosing a family of gameplay questions

Review: 2026-09-23. This is a compute-planning review of all 45 ranked entries, not a new gameplay search, proof audit or route closure. Existing verdicts and subjective counterexample estimates are unchanged.

Investigate a mechanism that several routes need, then reuse the result where its conditions actually hold. The 11 families below group possible gameplay exceptions by their shared missing connection. A label does not assert that a glitch exists. They are practical work packages, not a replacement for the theorem’s six formal movement-family obligations or a proof that all possible glitches have been enumerated.

Each rank has exactly one **primary** home for navigation. **Also helps** means that another route consumes a related result; it does not mean that settling this family retires that route. Downstream collection, shared proof contracts and a different start have separate workstreams so they cannot be mistaken for independent bypasses.

## Where I would start

- **F01 — floors and support:** best shared proof investment. Start by deriving the live query conditions of the existing elevator alignment result. This can settle the repeated grounded hold without pretending to settle every way into ground pound.
- **F11 — secret credit:** a sharply defined first invariant. Show that a missing credited secret corresponds to a real earlier touch, including a reload. This targets unearned credit, not the geometry of reaching every secret.
- **F08 — collision and contact:** the strongest remaining gameplay lead in this grouping. Start with the Act-3 rim approach from Rank 12B. Its 2–5% atlas estimate remains a subjective route judgment, not a probability that the family contains a glitch.
- **F06 — enemy transport:** useful shared search if a broader compute batch is wanted. Close the hard-fall and long-airborne gaps before treating the old finite Goomba graph as complete.

## How a compute batch earns a verdict

Choose a version, allowed start, actor/action domain and named claim before expanding the search. Use the actual generated source and existing proofs. Read-only replay logs can identify the first failure of a proposed invariant; favorable RNG choices still have to be choices the game can make. An enclosing, justified state analysis may prove a bound that a finite sample cannot.

A useful batch can (1) prove the named mechanism impossible under stated, meaningful conditions; (2) grant a clearly stated diagnostic setup and prove its payoff cannot help the target; or (3) produce a reproducible candidate and explain exactly which condition it breaks. A failed finite search reports only its tested domain. State which conditions were derived, which remain assumed and which ranked dependencies are actually discharged. Do not assume the desired useful combination merely to make a theorem tractable.

Keep that finish line fixed. Completing a conditional theorem does not require proving its entry conditions throughout the game. That applicability claim is a separate extension. The F02 follow-up list previously bundled several such extensions into one “bounded” batch; this understated the work. An imported result or a larger checked package is not, by itself, a discharged route obligation. Report the exact conditional closure and any wider claim separately.

The scope remains ordinary controller gameplay and defined, in-bounds glitches. No new A edge is the core input rule; the useful-negative-seed investigation specifically asks for A never pressed. Already-held-A variants need their real input predecessor. ACE, arbitrary state/code modification, invalid memory access and emulator/OS/network vulnerability methods are outside this workboard.
